# 高中生物双模型高精度打标：各一票起步，分歧按需追加

日期：2026-09-28。策略版本建议：`adaptive-q1d1-strict-intersection-v1`。

状态：**新策略执行器已实现，服务器任务尚未切换；准确率校准尚未完成。** 本文不是既有“全量各两票＋模型内部有分歧才补第三票”执行器的使用说明。

## 1. 目标与核心决定

业务优先避免错标，允许少选、漏标和暂不打标。不以两模型完整结果一致率、Jaccard或标签覆盖量作为正确性的替代指标。

拟采用的流程是：

1. 全量题目先由Qwen、DS各判断一次。
2. 两份Label集合相同且内容可靠时，该集合进入高精度待入库集合；相同且为空时，结束本题投票，不产出正标签。
3. 两份Label集合不同，则两个模型各追加一次，重新判断相同的完整候选集。
4. 对四票题，只保留**Qwen两票、DS两票全部选中**的Label；其余暂不保留，不用多数票补回来。
5. 两模型各第三票作为可选诊断/加强验证，不默认全量追加，也不自动救回此前有反对票的Label。
6. 共识只是放行候选条件。输入质量检查、已验证的风险拦截和独立抽审校准另行执行。

“只要不错标”是质量方向，不是统计上的零错误承诺。此前约定自动通过错标率上限为≤5%；是否达到需独立验证，不能仅由票型证明。

## 2. 与旧方案的区别

| 方案 | 起步请求 | 追加触发 | 保留口径 |
|---|---|---|---|
| 原固定六票 | Qwen三票＋DS三票全量 | 无自适应路由 | 可用于回放多种策略，不预设六票即正确 |
| 已有各两票＋条件第三票执行器 | Qwen两票＋DS两票全量 | 某模型自身两票集合/状态不一致 | 既有程序产生模型内多数集合，不能直接等同本文策略 |
| 本文新方案 | Qwen一票＋DS一票全量 | 两模型首票Label集合不同 | 所有已执行的有效票严格交集，按题–Label保留 |

本文新方案不是“两个模型各自2/3多数后再取交集”，也不是“总票数≥4就保留”。

## 3. 基本单元和输入约束

### 3.1 请求单元与决策单元

- HTTP判断以当前打标单元为单位：独立题、复合题小题、父题材料额外知识点单元。
- 是否追加请求按题/打标单元判断，因为一次请求会判断该题的完整候选集。
- 是否保留按`(question_id, label_id)`判断。同题可以保留A，同时暂不保留B和C。
- 比较集合使用Label ID的无序集合；顺序、reason文本和evidence措辞变化不算Label分歧。

### 3.2 所有票冻结相同输入

使用Hybrid Top25＋当前458个Label范围内的旧`knw_ids`补充候选。先去除重复ID，旧ID已在Top25内时不增加候选。旧标签只是候选召回补充，不是正确答案。

同一题的全部票必须保持题目正文、选项、解析、父题上下文、候选ID及顺序、候选代码映射、Label卡、prompt版本一致。以输入SHA和实际prompt SHA校验，不能只检查“候选ID集合相同”。

新流式请求记录逐题`prompt_sha256`。原历史证据没有此字段时，程序默认拒绝复用；仅在人工确认原prompt未变后，才可显式添加`--allow-legacy-missing-prompt-hash`兼容。该兼容模式仍校验已记录的输入/参数/版本/候选映射，但**无法验证原实际prompt内容**，须保留此限制，不宣称重复票输入已完整证明一致。

追加票仍使用完整的相同候选，不只发有分歧的Label；不展示前一票输出、投票计数、旧标签正确性暗示或另一模型的reason。若修改候选/释义/prompt，应视为新实验，不能混作原策略重复票。

## 4. 第一阶段：各一票

记Qwen第一票为`Q1`、DS第一票为`D1`，二者为有效且可用于标签判定的ID集合。

| 首票情况 | 路由 | 正标签处理 |
|---|---|---|
| `Q1 = D1 ≠ ∅`，质量检查通过 | `FIRST_PAIR_AGREEMENT` | 集合进入高精度待入库候选，不默认补票 |
| `Q1 = D1 = ∅`，请求有效且无未决状态 | `FIRST_PAIR_EMPTY` | 结束，无正标签；不制造负例金标 |
| `Q1 ≠ D1` | `FIRST_PAIR_DISAGREEMENT` | 各追加一票；首票交集暂存但先不最终发布 |
| 任一请求失败、截断或解析失败 | `REQUEST_PENDING` | 重试缺失的逻辑票，不增加投票次数 |
| 集合相同但上下文不足/需扩召/内容质检未通过 | `INPUT_OR_RECALL_REVIEW` | 不按一致直接放行；先处理未决状态 |

Label集合分歧触发第二轮；状态字段不一致单列为质量/召回问题，不伪装成普通票型。可将状态异常题额外请求作为诊断，但不能用重复票替代补图、补材料或补召回。

### 例：首票存在局部共识

```text
Q1 = {A, B}
D1 = {A, C}
```

整题触发第二轮。A虽然首票共标，仍随本题第二轮一起验证；B、C暂不保留。这样避免一边把A提前发布，一边又发现后续票反对A却不撤回。

## 5. 第二阶段：分歧题各追加一票

得到`Q2`、`D2`后，仅在四次逻辑票均成功且质量状态合格时计算：

```text
strict_keep_4 = Q1 ∩ Q2 ∩ D1 ∩ D2
```

该交集中的每个Label均为两模型各2/2选中。交集外项保持未保留，无须给老师逐题处理；业务允许漏标时，可直接暂缓这些项。

| 某Label的四票支持 | 处理 |
|---|---|
| Qwen 2/2，DS 2/2 | 四票共标，进入高精度待入库候选 |
| Qwen 2/2，DS 0/2；或相反 | 强跨模型分歧，暂不保留；需要时独立judge |
| 任一模型为1/2 | 存在模型内波动，暂不保留 |
| 两模型均0/2 | 本轮未选，不视为人工确认负例 |

```text
Q1 = {A, B}
Q2 = {A, B}
D1 = {A, C}
D2 = {A, B}

strict_keep_4 = {A}
```

B虽然得到3/4支持，仍不自动入库；C也不入库。不要求四次完整集合完全一样，其他Label的分歧不会阻止A被保留。

**四票共标是全部四次都选中。六票中的Q3/D1虽然总共四票支持，不属于这个条件。**

## 6. 第三阶段：可选加强验证，不用于多数救回

### 6.1 为什么不默认追加

在严格交集策略下，第三轮只可能维持或缩小保留集合：

```text
strict_keep_6 = strict_keep_4 ∩ Q3 ∩ D3
strict_keep_6 ⊆ strict_keep_4
```

前四票没有四票共标的Label，即使两个第三票都选中，也不能变成六票共标。如果`strict_keep_4`为空，再追加两票不会产生新的严格交集正例。

因此建议第三阶段默认关闭，仅对事先定义的高风险或随机验证样本执行：

- 检查四票保留集合是否还会被第三轮推翻；
- 收集模型内波动及强跨模型冲突的证据；
- 对长尾、实验类、综合类、旧释义风险Label进行定向诊断；
- 为未来比较“2/3多数＋独立judge”另一个策略版本提供数据。

长尾按此前独立题正样本少于300题的口径标记，只作为风险线索，不等于当前全量Label总量少于300。

### 6.2 执行第三轮后的结果处理

被选中参加第三轮的题，四票结果仍为暂定；第三轮完成后按六票严格交集发布。不允许发现第三票反对后仍称该项为“所有有效票一致”。若曾导出四票暂定结果，须记录撤销/版本更新。

| 六票逐Label状态 | 自动处理 |
|---|---|
| Q3/D3 | 保留候选，仍受输入质量及校准约束 |
| Q3/D2、Q2/D3、Q2/D2 | 不自动保留；诊断或独立judge |
| Q3/D0、Q0/D3 | 不自动保留；优先分析释义/任务边界，不继续盲目重复同模型票 |
| 其他状态 | 暂不保留 |

只有Q3/D3能通过本阶段严格规则。若希望恢复其他票型，必须启用独立、已校准的judge路由并保存来源，不得把judge补标说成投票共识。

未请求第三票是`NOT_REQUESTED`，不是0票、反对票，也不能复制第二票冒充第三票。

## 7. 共识之外的硬门槛

### 7.1 有效请求

一次逻辑票可有多次HTTP尝试，最终只能贡献一票。失败或无有效输出的请求不算反对票；`finish_reason=length`或响应未完整解析不能算成功空集合。

未知候选代码、证据校验失败、结构字段异常等按原精排校验规则处理并保存。不得为了提高完成率静默将解析失败降为`selected=[]`。

### 7.2 输入和状态

实际设问缺失、关键图像信息无法从文本恢复、缺必要父题材料、内容复核未通过时，共识不能消除信息不足。

有图片URL并不代表当前文本模型看到了图片。也不能只因某题有图片就全部筛掉，应判断文字是否足够完成当前设问。

`context_insufficient`、`need_expand_recall`、`needs_review`、`usable_for_training`及已审计排除规则不能被集合一致覆盖。需扩召若改变输入，补跑作为新输入版本处理，不能直接混入原两票/四票。

### 7.3 系统性错标

双模型也可能共同把背景知识扩成标签、被解析后附知识误导、混淆相邻Label或忽略对象/任务范围。重复投票只能观察稳定性，不能证明这种稳定判断正确。

通用或较宽Label只要实际符合释义，可以合理共标；不能仅因名称宽泛自动排除。反之，共享词语、遗传符号或机制不能替代具体对象和任务匹配。

例：题干给出基因治疗描述，但只问“从变异角度属于哪种变异”，需警惕把“基因治疗”背景扩成直接考点。此例是诊断假设，不是已校准的普适自动排除规则。

## 9. 结果状态及训练准入

建议分开保存投票结论和质量结论，而不是只输出一个`match=true`。

| 字段 | 含义 |
|---|---|
| `policy_version` | 本策略规则版本 |
| `actual_vote_count` | 当前实际成功逻辑票数0–6；阶段未完成时可以是1、3或5 |
| `completed_stage_vote_count` | 最近完整完成阶段的票数：2、4或6；尚无完整阶段时为空，不代表当前所有成功票数 |
| `executed_vote_ids` | 实际票身份，不能只存总票数 |
| `qwen_support / ds_support` | 该Label在本题已执行票中各模型支持数 |
| `selection_status` | 首票共识/四票严格交集/六票严格交集/未保留 |
| `escalation_reason` | 首票集合分歧、指定诊断抽样、输入问题等 |
| `quality_status` | 合格/上下文不足/需扩召/内容待复核/请求待完成 |
| `calibration_status` | 未校准/独立验证通过/风险层暂缓 |
| `training_eligible` | 同时满足投票、质量、已冻结放行策略后才为true |

输入可靠、严格共识的项先进入`HIGH_PRECISION_CANDIDATE`。在相关质量层完成独立抽审校准前，不将“一致”直接写成人工金标或自动批准训练数据。

未保留的Label表示“本策略不给正标签”，不等于“确定不相关”。部分标签题不应用作穷尽式负例：训练若把未列出的458个Label全当负例，会把允许的漏标变成错误监督，应使用相应的部分标签/负例掩码或单独验证负例。

业务接受漏标后，不必为所有未保留项排教师任务。教师优先检查拟保留的正标签及高影响错误簇；少量未保留项用于诊断覆盖损失即可。

## 10. 先用既有六票回放验证

### 10.1 正确回放需要原始票身份

先固定六票都成功且输入一致的题，再按真实`qwen1、ds1`首票判断是否分歧。只有分歧题才在回放中读取`qwen2、ds2`，第三票按冻结抽样路由使用。

逐Label的Qx/Dy票数表不能完整回放本策略，因为它丢失了第一票是否选中及整题首票集合关系。回放必须读取六份逐题输出；不能只从16格数量推断通过量。

可额外轮换9种Qwen/DS首票配对进行敏感性分析，二票顺序须预先固定。不得挑“表现最好的首票组合”作为上线收益；它们也不是9份独立样本。

### 10.2 回放报告至少输出

1. 分母：六票共同成功题、题型、冻结输入版本；未成功题和运行中快照偏差单列。
2. 第一轮完整集合一致非空、同时为空、集合分歧的题数及比例。
3. 第二轮四票交集非空、为空、相比首票交集撤回的题–Label数量。
4. 最终保留题数、题–Label对数、每题保留标签数及逐Label分布。
5. 相比六票严格交集的新增项、减少项，区分第一阶段和第二阶段通过来源。
6. 三类题型、旧ID是否补出候选、候选rank、历史释义风险、长尾等分层。
7. 请求节省量与实测速率；不能把少请求直接等同同比例缩短墙钟时间。

如果不启用额外质量过滤，固定输入下六票严格交集应是本策略两阶段保留集合的子集。此关系可作实现一致性测试；出现相反结果需先查票身份、输入版本、状态过滤或聚合逻辑。

### 10.3 真正决定是否安全的是抽审保留项

优先抽审：首票共同选中但未六票共识的项、四票共标但第三轮有反对的项，以及六票共识对照。它们用于检验减少票数带来的错标风险。

教师估计总体错标率的样本须按真实保留总体概率抽样，记录层体量、抽样概率和随机种子；高风险定向样本与随机验证样本分开。按题/父题簇处理相关性，逐Label风险不能被总体均值掩盖。

40例快速抽审只用于发现风险，不能证明≤5%；之前的正样本覆盖、负样本和Luna审核用于排序与诊断，除经过独立核验的教师标签外，不作为金标。

## 11. 请求成本与第三票收益

令N为第一阶段有效处理的题数，D为其中首票Label集合不同、进入第二阶段的题数，R为额外进入第三阶段的题数，且`R ≤ D`。主流程逻辑请求量：

```text
各一票＋分歧各补一票：2N + 2D
再对R题各补第三票：  2N + 2D + 2R
固定六票：           6N
```

这是逻辑请求数，不包括HTTP重试、输入修复后的新版本重跑或独立judge请求。第三阶段若要抽查首票完全一致题，应另列验证请求量，不混入`R ≤ D`主流程。

举例仅为成本说明：若首票分歧率为50%，不启用第三轮，则平均3次逻辑请求/题，较固定六票减少50%。当前真实分歧率须回放首票输出计算，不能拿两模型三票多数集合差异率代替。

第三票对严格交集的收益是进一步排除不稳定正标签，不是恢复召回。是否值得启用，比较它撤回了多少项，以及这些撤回项经独立审核究竟有多少确为错标。

## 12. 目录、断点续跑与复用原则

新策略必须使用独立目录，建议结构如下；这是设计，不是已存在的运行路径：

```text
fine-full-six/
  adjudication-no-thinking/              # 原固定六票，不覆盖
  adjudication-adaptive-2plus1-w35/       # 既有另一策略，不混用
  adjudication-adaptive-q1d1-strict-v1/   # 本策略独立目录
    run_manifest.json
    controller.lock
    seed_report.json
    votes/{qwen1,ds1,qwen2_disagreement,ds2_disagreement}/
    votes/{qwen3_diagnostic,ds3_diagnostic}/
    routing/{stage2,stage3}/
    consensus/                          # 逐题及逐Label保留/未决结果
    quality/                            # 输入、输出、召回质检
    aggregation/                        # 父题小题并集＋材料额外
    reports/
```

每票独立证据、状态数据库和日志；同目录独占控制器锁。已完成的有效逻辑票续跑跳过，失败票重试，不重复计票。保留冻结的追加题清单及触发原因，不根据不断变化的临时输出随意改分母。

可以复用原运行第一票及后续已成功票，但先核对票身份、模型、输入SHA、prompt、请求参数和排除规则，保存复制来源/校验和。不要为了“凑一致”选择性取某次成功输出，也不要将一票的HTTP重试当多票。

迁移应在原任务停止后或一致性快照上进行；原目录保留，不能覆盖、硬链接共同写入或伪造未运行的票。本文不授权停止服务、停止任务或启动新跑数。

## 13. 目前推荐落地顺序

1. 用现有六票回放“各一票＋分歧各补一票”，先看实际请求节省及新增保留项。
2. 对新增保留项做独立概率抽审，并单列输入质量、Label边界及题型风险。
3. 冻结确认后的共识规则、质量过滤和放行范围，再实现新执行器及迁移方案。
4. 默认不全量启用第三轮；仅对已冻结的验证样本/风险层按需追加。
5. 所有自动入库项继续随机质检；发现系统性错标时暂停对应风险层，不能靠增加同模型重复票掩盖。

## 14. 阅读自检

- 首票两个集合顺序不同但ID相同，要追加吗？不追加。
- 首票集合相同但上下文不足，能直接通过吗？不能。
- 四次结果都包含A，但B/C有分歧，A能保留吗？能进入待入库候选。
- 六票Q3/D1共四票支持，能按四票共标通过吗？不能。
- 第二轮严格交集为空，第三轮能恢复严格共识标签吗？不能，除非另开已校准judge路由。
- 第三票没有运行，能当反对票或复制前票吗？不能。
- 第一轮失败重试三次算三票吗？不算，仍是一张逻辑票。
- 不保留的Label能作为确定负标签训练吗？不能仅凭此策略认定。
- 双模型都选中就保证正确吗？不保证，仍有共同系统性错误风险。

## 15. 当前实现与服务器运行方式

入口为`scripts/run_qwen_ds_strict_adaptive_full.py`，核心为`src/bio_know_tag/strict_adaptive_vote_runner.py`。复用原有流式单票执行器及SQLite断点记录，未改变原精排prompt、Top25＋旧ID候选和旧执行器行为。

当前采用阶段屏障：第一轮全量两票完成后，冻结第二轮分歧清单；第二轮完成后再冻结可选第三轮诊断清单。不是每道题两票一完成便即时补票。每阶段两模型并行、每模型35并发。

`--third-diagnostic-limit 0`默认不跑第三轮；设置正整数时，按`--diagnostic-seed`对第二轮题号作确定性哈希优先抽样，最多10,000题，顺序仍与原输入一致。该抽样仅是诊断，不能冒充校准金标或整个保留总体的概率验证样本。

`--seed-from-six-vote`从已停止的固定六票目录读取原`qwen1/ds1`成功证据；第二轮及第三轮仅复制对应原`qwen2/ds2`、`qwen3/ds3`中被路由题的证据。校验模型、配置、输入SHA、prompt版本、逐题实际候选映射及已记录的prompt SHA；复制结果而非链接，重建新SQLite，失败/未完成题才请求服务。不修改原文件，不挑选其他票的输出。原目录必须有`controller.lock`和相关票manifest，参数不兼容时拒绝复用。Linux上额外检查残留/孤儿票进程，复制前后检查源evidence大小/修改时间/文件身份，避免误把仍在写的旧目录当作已停止。

缺旧prompt指纹的显式兼容复用，会在各票`seed_provenance.json`记录`prompt_hash_unverified_rows`，总报告记录`seed_prompt_hash_unverified_rows`（证据行数，不是唯一题数）。不伪造旧记录的prompt SHA。原目录在复制期间必须保持停止；Linux外不能执行`/proc`进程检查，仍需要人工确认无源文件写入者。

结果位置：`consensus/predictions.jsonl`及`consensus/report.json`。`selected_labels`保存严格交集供审核；`high_precision_candidate`还要求质量检查通过，`training_eligible`及`usable_for_training`当前均为false，等待独立校准，不静默批准训练数据。父题汇总仍使用现有独立聚合流程，本执行器不把子题标签回灌到父题材料单元，也不自动执行最终父题汇总。

以下命令不停止旧任务；启用旧结果复用前，应确认旧控制器及其票进程已经停止。不允许两个控制器同时写旧目录。

```bash
cd /local_data/zhangyonglin/Bio-Know-Tag
RUN='runtime/20260924-104413-biology-s85-reuse-preprocess'
OLD="$RUN/fine-full-six/adjudication-no-thinking"
NEW="$RUN/fine-full-six/adjudication-adaptive-q1d1-strict-v1"
mkdir -p "$NEW"
LOG="$NEW/controller-$(date +%Y%m%d-%H%M%S).log"

nohup env PYTHONPATH=src python -u scripts/run_qwen_ds_strict_adaptive_full.py \
  --units "$RUN/unified/retrieval_units.jsonl" \
  --candidates "$RUN/fine-full-six/legacy/candidates.jsonl" \
  --labels configs/labels.jsonl \
  --run-dir "$NEW" \
  --seed-from-six-vote "$OLD" \
  --workers-per-vote 35 \
  --max-tokens 1024 --retries 5 \
  --third-diagnostic-limit 0 \
  > "$LOG" 2>&1 &
printf '%s\n' "$!" > "$NEW/controller.pid"
printf 'LOG=%s\n' "$LOG"
```

上面省略的模型、端口、超时、temperature、流式和关闭thinking均使用第3节的默认值。不复用旧结果时从命令中移除`--seed-from-six-vote`，但必须使用新的空目录。

此前固定六票的旧证据通常未记录prompt SHA。因此上面的严格模式示例可能拒绝旧结果复用；只有确认其prompt与当前冻结版本相同后，才在首次启动命令添加`--allow-legacy-missing-prompt-hash`。该选项也纳入manifest，不能中途在原新目录开关。若无法确认原prompt，使用新目录重跑，不靠兼容开关绕过已知不一致。

续跑使用原目录及完全相同的参数。不能在原目录把`--third-diagnostic-limit 0`改为100，或修改模型、prompt、候选、Label卡、并发等；manifest不一致会拒绝续跑，应新建版本目录。每票进度在`votes/<vote>/report.json`和`runner.log`，阶段在`progress.json`，控制器输出在上面的LOG。新目录不适用旧“固定六票全量分母”的ETA脚本。

完成阶段的共识报告提供2/4/6票数。阶段未完成时尚不发布最终共识文件，查询每票状态即可；请求失败须续跑补齐，不将未完成票算成反对票。
